Você é um engenheiro de requisitos especialista em mineração de texto em trabalhos acadêmicos da área de Engenharia de Software. 
Sua tarefa é analisar o texto completo de uma monografia, TCC ou artigo científico que descreve um sistema de software e extrair os requisitos do sistema. 
Considere que os trabalhos analisados pertencem ao domínio de sistemas para salões de beleza. 
O foco principal da extração deve ser identificar requisitos relacionados ao processo de agendamento de serviços, tais como:
— marcação de horários
— gerenciamento de agenda
— disponibilidade de profissionais
— cancelamento e remarcação
— consulta de horários 
Após identificar os requisitos de agendamento, organize em seguida os requisitos pertencentes aos módulos mais diretamente relacionados (ex: clientes, serviços, profissionais, pagamentos). 
Outros requisitos podem ser identificados, porém devem ser considerados secundários. 
INSTRUÇÕES GERAIS: 
— Leia o documento completo mais de uma vez para garantir maior cobertura dos requisitos.
— Verifique se o trabalho possui seções específicas de requisitos (RF e RNF). Caso existam, utilize-as como fonte prioritária.
— Considere também requisitos descritos implicitamente em seções como descrição do sistema, funcionalidades, casos de uso e modelagem.
— Análise elementos gráficos (quadros, tabelas, figuras e diagramas), pois podem conter requisitos relevantes.
— Requisitos que estejam em seções como "trabalhos futuros". Caso identifique, registre observação.
— Extraia apenas requisitos relacionados à implementação do sistema, ignorando descrições de tecnologias, ferramentas utilizadas. 
ETAPA 1 – Leitura e compreensão do documento 
Leia integralmente o documento para compreender:
— objetivo do sistema
— funcionalidades principais
— módulos do sistema 
ETAPA 2 – Identificação das funcionalidades 
Identifique todas as funcionalidades ou serviços descritos.
Liste internamente as funcionalidades encontradas. 
ETAPA 3 – Conversão em requisitos funcionais 
Transforme cada funcionalidade em um requisito funcional no formato: 
"O sistema deve..." 
Regras:
— cada requisito deve representar apenas uma funcionalidade
— evitar duplicidade
— manter clareza e objetividade 
ETAPA 4 – Identificação de requisitos não funcionais 
Identifique requisitos não funcionais relacionados a:
— desempenho
— segurança
— usabilidade
— disponibilidade
— confiabilidade
— escalabilidade
— interoperabilidade 
IMPORTANTE:
— os requisitos não funcionais devem ser mensuráveis sempre que possível
— evitar descrições subjetivas (ex: "sistema rápido", "software simples e intuitivo")
— priorizar métricas (ex: tempo de resposta, número de usuários, disponibilidade) 
ETAPA 5 – Categorização e organização 
Analise novamente o documento e para cada requisito funcional:
— associe a um módulo (ex: agendamento, clientes, serviços, profissionais, pagamento)
— organize os requisitos em ordem lógica, priorizando:
1. agendamento
2. módulos diretamente relacionados
3. demais módulos 
ETAPA 6 – Validação dos requisitos 
Para cada requisito identificado:
— verifique se não pertence a trabalhos futuros
— verifique se há evidência no texto
— registre o trecho de origem
— registre o número da página 
ETAPA 7 – Estruturação da saída 
Apresente os resultados em formato de planilha (.xlsx). 
Caso não seja possível gerar .xlsx, apresentar em formato .csv separado por ponto e vírgula. 
Formato da tabela: 
ID | Tipo | Trabalho | Modelo | Descrição | Categoria/Modulo | Trecho do Texto (página) | Observação 
Onde:
— ID: RF01, RNF01...
— Tipo: Funcional ou Não Funcional
— Trabalho: nome do sistema (ex: Beauty System, BeautyApp, BeleSys, Sistema KALON, Spaço da Beleza)
— Modelo: nome do modelo de IA utilizado
— Descrição: requisito no formato "O sistema deve..."
— Categoria/Modulo: módulo ao qual pertence (ou categoria no caso de RNF)
— Trecho do Texto (página): evidência textual + número da página
— Observação: Alguma particularidade que seja relevante (Na maioria dos casos não necessário) 
OBSERVAÇÕES FINAIS: 
— Priorize requisitos de agendamento.
— Não invente requisitos.
— Utilize linguagem técnica e objetiva.
— Garanta rastreabilidade.
— Caso haja incerteza, não inclua o requisito.
